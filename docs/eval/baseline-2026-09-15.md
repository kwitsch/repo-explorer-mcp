## Metrics that are `n/a`, and why

| Metric | Status | Why |
|---|---|---|
| `cached_ratio`, `cache_read_tokens`, `cache_write_tokens` | **n/a by construction** | 0.8.0 has no cache-token telemetry anywhere. `usage_from` in `crates/repo-explorer-llm/src/lib.rs` copies only `prompt_tokens`/`completion_tokens` out of genai's `Usage` and drops `prompt_tokens_details.{cached_tokens, cache_creation_tokens}`. No pre-QW-0 run can contain these fields — a 0% here would be a fabrication, so the scorer prints `n/a — provider reports no cache activity` instead. |
| `total_ms` (server-side per-query wall clock) | **n/a — field absent** | Emitted by the QW-0 `QueryMetrics` record, which 0.8.0 does not emit. The harness-side `latency_ms` above is present and is the comparable stand-in for now (it includes MCP round-trip, so AFTER-vs-BEFORE on `latency_ms` is apples-to-apples; `total_ms` will only exist on the AFTER side). |
| `early_exit_route` | **n/a — field absent** | Same reason. The 10 early-exit rows cannot be split into `confidence` / `unique-symbol` / `none`. |
| `outer_followup_rate` | **structurally unmeasurable** | `run.py` is a scripted MCP client: exactly one call per query, never a follow-up. Needs the Layer B/C outer-agent arm (`eval/baseline.py`, `claude_loop.sh`, `judge_prompt.md`), none of which exists. Treat as unmeasured, not as zero. |
| `cost_per_query` | **computed, but dated** | Derived from `score.py`'s `PRICES` table, **captured 2026-09-15** from <https://ai.google.dev/pricing>. Those are the published *tier* rates (Flash / Flash-Lite) applied to every model in that tier; the individual 3.x per-model rates were not re-verified on the capture date. Valid as a **relative** signal between two runs scored with the *same* table; not an invoice. If the table or the failover chain changes, this baseline's dollar figure must be recomputed before comparing. |

## Other caveats on these specific numbers

- **`tokens` excludes reasoning tokens.** It is `TokenBudget::spent()` = Σ(prompt + completion).
  Reasoning tokens are logged per provider call but never enter the budget, so the token
  baseline understates real spend on a reasoning model. `cost_per_query` *does* charge them as
  output tokens, so the two are not derivable from each other. If QW-0 ever folds reasoning
  tokens into the budget, this baseline shifts and must be re-taken.
- **`tokens = 0` on cache and early-exit rows by construction**, which is why the token line is
  reported both ways. 14 of 64 rows (4 cache + 10 early-exit) are 0-LLM. Compare all-rows mean
  to all-rows mean and LLM-rows mean to LLM-rows mean, never across.
- **Provider-call count in the non-QW-0 section of the report is inflated** (`224 total`, 103 of
  them fieldless `outcome=<none>` ghosts). Those are an artifact of the old `provider call`
  stderr matcher in `run.py`, fixed on this branch but baked into these stored rows. The QW-0
  cost block is unaffected: a call reporting no usage costs 0 and is not counted among the 103
  priced calls.
- **Heavy model drift in this run**: pinned `gemini-3.8-flash`, but all six chain models were
  served, with 16 `rate_limited` and 2 `quota` outcomes. Token and cost figures therefore mix
  Flash and Flash-Lite tiers. An AFTER run with a different drift profile will differ on cost
  for reasons unrelated to any code change — compare `tokens_per_query` first, cost second.
- **22 stage mismatches**, all `expected=fallback observed=verify` on the imprecise (`I*`)
  queries. That is a ground-truth expectation issue in `eval/queries/*.yaml`, not a regression;
  noted so it is not read as one in the AFTER diff.

## Reproduce this baseline (offline, zero API calls)

```bash
cd /home/kwitsch/repos/repo-explorer-mcp
uv run --with pyyaml eval/score.py results/20260907T091929 --csv-out docs/eval/baseline-2026-09-15.csv
```

That is the whole thing. It reads `results/20260907T091929/*/pass*.jsonl` and the pinned
corpus checkouts under `~/repos/eval-corpus/`, starts no server, and needs no `GOOGLE_API_KEY`.
The `--csv-out` flag writes the per-query CSV and, as a sibling, the `.aggregate.csv`.

## Produce a comparable AFTER run

Prerequisites, all of them (see `eval/CLAUDE.md` and the `run-eval` skill):

1. The new binary is installed to `/home/kwitsch/.local/bin/repo-explorer-mcp` — `run.py`
   hard-codes that path and never builds the workspace. Confirm with
   `repo-explorer-mcp --version`; it must no longer report `0.8.0`.
2. **Claude Code is closed** — the standalone binary and any interactive session share one
   per-user `codebase-memory-mcp` daemon and one Gemini quota.
3. `GOOGLE_API_KEY` is exported, with quota left. A run dominated by `quota` outcomes is not a
   valid signal.
4. The pinned corpus clones exist at `~/repos/eval-corpus/{self,requests}` (`repos.toml` pins).

Then:

```bash
cd /home/kwitsch/repos/repo-explorer-mcp
uv run --with mcp --with pyyaml eval/run.py --repos self requests --passes 2
uv run --with pyyaml eval/score.py results/<new-run-id> --csv-out docs/eval/after-<date>.csv
```

Same repos, same pass count, same `eval/config/default.toml`, and the same `score.py` `PRICES`
table as this baseline — otherwise the two aggregate CSVs are not comparable. Diff
`docs/eval/baseline-2026-09-15.aggregate.csv` against the AFTER aggregate CSV; the three lines
that matter for QW-0 are `llm_calls.mean`, `tokens_all.mean` / `tokens_llm_rows.mean`, and
`stage_exit.*`, with `cand_recall@top_k` and the hallucination count as the do-no-harm guard.
